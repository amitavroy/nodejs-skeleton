# __APP_NAME__

TypeScript monorepo (npm workspaces): `apps/server` (NestJS + Drizzle + Postgres), `apps/web` (Next.js App Router + Tailwind + TanStack Query). The two apps are independent and share no code or packages. The app runs on the host (`npm run dev`: API on `API_PORT` (3001), web on `WEB_PORT` (3000); both set in `.env`); infrastructure runs in Docker (`make up`): Postgres (pgvector/pgvector:pg17), Redis, Mailpit, pgAdmin, Dozzle. `make help` lists commands.

## Working agreement
- Work is driven by plans in `docs/plans/` (see its README). Execute one plan per session; don't wander beyond its Scope.
- When a plan is finished, tick its tasks, fill in its Outcome and update the index.
- Branches: **work on a plan always happens on its own branch**, never on `main`. Before implementing any task of a plan, run `/start-plan NNNN` (or follow `.claude/commands/start-plan.md` by hand): it creates `<issue>-<slug>` from the plan's GitHub issue (`plan-NNNN-<slug>` if it has none), pushes it, commits the plan there, and only then starts work. Reference the issue (`#123`) in commit messages.
  - Small changes outside any plan (a typo, a config tweak, a one-line fix) may be made on `main`. If it is unclear whether something is plan work or a small change for `main`, ask before touching any file.
- `docs/architecture.md` is **binding for all new code**. Check its ADRs before changing the data model or layering. Rules you must not break:
  - Layering (server): controller → service → repository. Controllers never touch the DB; services never import Drizzle or Express; Drizzle is used only inside repositories, which return domain types.
  - Server: Zod schemas live next to the module (`<feature>.schemas.ts`) and are the source of truth for DTOs; infer types from them and wrap them with `createZodDto` (nestjs-zod). Controllers take `@Body()`, `@Query()` and `@Param()` as those DTOs (path params too, never `ParseIntPipe`); the global `ZodValidationPipe` validates them and failures answer 422 through `AllExceptionsFilter`.
  - The apps share no code. The web app keeps its own hand-written API types in `apps/web/src/types.ts`; when an API response changes, update them in the same change.
  - No `process.env` outside `apps/server/src/config.ts`.
  - Every endpoint is documented in OpenAPI in the same change, derived from its Zod DTOs via `@nestjs/swagger` (see "API documentation" in `docs/architecture.md`). Swagger UI is at `/docs` on the API port. An endpoint without `@ApiTags`, `@ApiOperation({ summary })`, and a `@ZodResponse`/`@ApiResponse`/`@ApiErrorResponse` for every status it can return is not finished.
  - Logging: pino JSON; every line carries `requestId` automatically. Add domain IDs only (`{ itemId }`), never log secrets. Never use `console.log`. Output goes to stdout, or to `storage/logs/YYYY-MM-DD.log` when `LOGS_AS_FILE=true`; code never opens log files itself.
  - Services throw `DomainError` subclasses; the global error handler shapes the response. Error body is always `{ code, message, details?, requestId }`. Validation errors are 422.
  - Slow or heavy work (rendering, transcoding, imports) never runs inside a request handler: queue it as a job (BullMQ on Redis) through the injected `JobQueue` (`JOB_QUEUE`), never by importing `bullmq` in a service. Handlers in `jobs/job-handlers.ts` stay thin (one service call). The requestId travels with the job automatically; see "Long-running work" in `docs/architecture.md` for how to add a job.
  - Outgoing email goes through Mailpit in dev (SMTP_HOST/SMTP_PORT); never hard-code a mail host.
  - Third-party integrations (mail, job queue, later S3, payments, CLI tools like FFmpeg) live in `integrations/<name>/`: an interface + DI token (`<name>.interface.ts`), one or more implementations, and a module that is the **only** place the binding is chosen (e.g. by `MAIL_DRIVER`). Services inject the token (`@Inject(MAIL_SENDER)`); tests use `overrideProvider`. Plain modules (repositories, services) need no interface.
  - List endpoints return `PaginatedResponse<T>`.
  - No `any`; one class per file; kebab-case file names with a role suffix (`items.service.ts`, `.controller.ts`, `.repository.ts`, `.module.ts`, `.interface.ts`).
  - Web: data via TanStack Query with loading, error and empty states; show 422 `details` on the matching form field.
  - Web UI is built with **shadcn/ui** (mandatory). Add primitives with the shadcn CLI (`npx shadcn@latest add <component>`, run in `apps/web`) into `src/components/ui/`; never hand-roll a button, input, table, dialog, form, etc. that shadcn provides, and don't add another component library. Compose shadcn primitives for anything bigger. Forms: shadcn `Field` + react-hook-form + Zod.
  - Web: components used by one page live next to it in a private `_components/` folder (`src/app/<route>/_components/items-table.tsx`, `items-form.tsx`). The `_` prefix keeps the folder out of routing, so it never becomes a URL segment. `page.tsx` stays thin and composes them. Only components shared by several routes go in `src/components/`; shadcn primitives stay in `src/components/ui/`.
- Server is CommonJS, built and tested with SWC (Nest DI needs decorator metadata, which esbuild/tsx don't emit). Relative imports have no file suffix. Use `__dirname`, not `import.meta`.
  - Web: the API is `apps/server` only. Do not add Next API routes (`route.ts`) or server actions; the browser calls same-origin `/api/*`, which `next.config.ts` forwards to the API. Pages are client-rendered with TanStack Query; use server components only for static layout.
- Schema-first: the Zod schema is the single source of truth for validation, types and docs. Import `z` from `zod` and DTO helpers from `nestjs-zod`.
- Every change ships with tests (`apps/server/test`, Vitest + supertest; `createTestApp()` builds the real `AppModule` on in-memory Postgres (PGlite) with fake job queue and mail, so no Docker is needed). Before finishing: `npm run typecheck && npm test`.
- **Never commit until the user explicitly says to commit** ("commit this", "you can commit now"). Finishing a task, a plan, or a request to make changes is not permission to commit; leave the changes uncommitted and say they are ready. The one standing exception is the plan-file commit `/start-plan` makes, because running it is the request. Permission covers that one commit, not later ones.
- After changing `.env`, use `make restart s=<service>` (plain `docker compose restart` does not reload it).
- Schema changes: edit `apps/server/src/db/schema.ts`, run `npm run db:generate`, commit the generated migration. Migrations apply on server start.
